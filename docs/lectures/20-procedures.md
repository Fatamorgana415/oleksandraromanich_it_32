# Лекція 20. Процедури у PostgreSQL

*Лекція 19 закінчилась пасткою: функція не може сама зробити `COMMIT`
чи `ROLLBACK` — вона завжди виконується всередині транзакції
викликача. Але іноді потрібно саме це: іменований, повторно
використовуваний блок логіки (як атомарна транзакція з Лекції 13), що
сам вирішує, коли зафіксувати зміни. Для цього в PostgreSQL є окремий
вид об'єкта — **процедура**.*

## 1. CREATE PROCEDURE — без RETURNS

```sql
CREATE OR REPLACE PROCEDURE mark_animal_status(p_id INTEGER, p_status TEXT)
LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE animals SET status = p_status WHERE id = p_id;
END;
$$;
```

Синтаксично процедура схожа на функцію (Лекція 19), але без
`RETURNS` — процедура не повертає значення як результат виразу.
Параметри в дужках так само з типами; тіло — так само між `$$`.

## 2. Викликається через CALL, не SELECT

```sql
CALL mark_animal_status(1, 'вибув');
```

```sql
SELECT mark_animal_status(1, 'x');
```

```text
ERROR: mark_animal_status(integer, unknown) is a procedure
HINT: To call a procedure, use CALL.
```

Процедуру НЕ можна викликати через `SELECT`, як функцію — потрібна
окрема команда `CALL`: спроба `SELECT` завершується
помилкою з чіткою підказкою. Це не довільне обмеження синтаксису — це
відображає принципову різницю: процедура не є виразом, що повертає
значення для використання в запиті, а самостійною дією.

## 3. Головна причина існування процедур: внутрішній COMMIT

```sql
CREATE OR REPLACE PROCEDURE bulk_mark_all_active()
LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE animals SET status = 'на обліку' WHERE status IS DISTINCT FROM 'на обліку';
    COMMIT;
    RAISE NOTICE 'Оновлено і зафіксовано';
END;
$$;

CALL bulk_mark_all_active();
```

На відміну від функції (Лекція 19, розділ 5), процедура МОЖЕ містити
`COMMIT` (і `ROLLBACK`) прямо у своєму тілі: виклик
успішно виконується й фіксує зміни. Це особливо корисно для
процедур, що обробляють великий обсяг даних частинами: кожна частина
може фіксуватись окремо, не чекаючи завершення всієї процедури.

## 4. Function проти Procedure — підсумкове порівняння

| | Function (Лекція 19) | Procedure |
|---|---|---|
| Оголошення | `RETURNS тип` | без `RETURNS` |
| Виклик | `SELECT func(...)` | `CALL proc(...)` |
| Повертає значення для запиту | так | ні |
| `COMMIT`/`ROLLBACK` усередині | заборонено (помилка) | дозволено |
| Типове призначення | обчислення, що використовується в SQL-запиті | самостійна дія / послідовність змін |

## 5. Практичний шаблон: атомарна пара як процедура

```sql
CREATE OR REPLACE PROCEDURE sell_car(p_car_id INTEGER, p_client_id INTEGER, p_price NUMERIC)
LANGUAGE plpgsql
AS $$
BEGIN
    INSERT INTO sales (car_id, client_id, sale_date, sale_price)
    VALUES (p_car_id, p_client_id, CURRENT_DATE, p_price);

    UPDATE cars SET status = 'продано' WHERE id = p_car_id;

    COMMIT;
END;
$$;

CALL sell_car(5, 3, 980000);
```

Це — та сама атомарна пара `INSERT` + `UPDATE` з Лекції 13, тепер
оформлена як іменована, повторно використовувана процедура: замість
того, щоб щоразу вручну писати `BEGIN`/два запити/`COMMIT`, достатньо
одного виклику `CALL sell_car(...)`.

## 6. Проблема: процедура без перевірок

Процедура `sell_car` із розділу 5 виконує обидві дії атомарно, але нічого не перевіряє. Подивимось, що станеться, якщо спробувати продати той самий автомобіль двічі. Для прикладу візьмемо таблиці `cars` (три автомобілі зі статусом `'в наявності'`), `clients` і `sales`:

```sql
CALL sell_car(1, 1, 780000);   -- Іваненко купує Skoda
CALL sell_car(1, 2, 790000);   -- Шевченко «купує» ту саму Skoda
SELECT COUNT(*) FROM sales;
```

```text
 count
-------
     2
```

Обидва виклики пройшли без помилок: у таблиці `sales` тепер два продажі одного автомобіля. Транзакція захистила від «розірваної пари» операцій, але від логічної помилки не захищає: базі невідомо, що продавати можна лише авто в наявності. Це правило бізнесу, і його потрібно записати в самій процедурі.

## 7. Процедура з перевірками

Додамо до `sell_car` змінну й дві перевірки перед будь-якою зміною даних:

```sql
CREATE OR REPLACE PROCEDURE sell_car(p_car_id INTEGER, p_client_id INTEGER, p_price NUMERIC)
LANGUAGE plpgsql
AS $$
DECLARE
    v_status TEXT;
BEGIN
    SELECT status INTO v_status FROM cars WHERE id = p_car_id;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'Автомобіля з id % не існує', p_car_id;
    END IF;

    IF v_status IS DISTINCT FROM 'в наявності' THEN
        RAISE EXCEPTION 'Автомобіль % уже має статус "%"', p_car_id, v_status;
    END IF;

    INSERT INTO sales (car_id, client_id, sale_date, sale_price)
    VALUES (p_car_id, p_client_id, CURRENT_DATE, p_price);

    UPDATE cars SET status = 'продано' WHERE id = p_car_id;

    COMMIT;
END;
$$;
```

Повторний продаж Skoda тепер відхиляється, так само як і продаж неіснуючого автомобіля:

```sql
CALL sell_car(1, 2, 790000);
CALL sell_car(99, 2, 1);
```

```text
ERROR:  Автомобіль 1 уже має статус "продано"
ERROR:  Автомобіля з id 99 не існує
```

Для автомобіля, що справді в наявності, виклик `CALL sell_car(2, 2, 990000)` проходить, і статус змінюється на `'продано'`. Порядок дій важливий: спочатку перевірки, потім зміни, і лише в кінці `COMMIT`. Така послідовність відсіює некоректні виклики, тож до зміни даних доходить лише допустимий запит. Умову записано через `IS DISTINCT FROM`, а не через `<>`: якщо статус раптом буде `NULL`, звичайне порівняння дало б невизначений результат і пропустило б продаж (Лекція 19, розділ 7). Від двох одночасних викликів ця перевірка сама не захищає: обидва можуть прочитати `'в наявності'` до того, як перший встигне змінити статус. Це той самий сценарій двох продавців із Лекції 12. Для таких випадків рядок читають із блокуванням (`SELECT ... FOR UPDATE`), але це вже за межами лекції.

## 8. Пастка: COMMIT усередині явної транзакції

Процедура з `COMMIT` у тілі працює, коли її викликають як окрему команду. Але якщо виклик стоїть усередині транзакції, відкритої вручну через `BEGIN`, процедура не має права закрити чужу транзакцію:

```sql
BEGIN;
CALL sell_car(3, 1, 690000);
```

```text
ERROR:  invalid transaction termination
```

Це та сама помилка, що й у функції з Лекції 19, і причина та сама: транзакцію, яку відкрив хтось інший, тіло процедури завершувати не може. Практичний висновок: процедури, що містять `COMMIT`, викликають через `CALL` на верхньому рівні, а не всередині `BEGIN ... COMMIT` у клієнтському коді. Після помилки транзакцію в `psql` потрібно закрити командою `ROLLBACK`; у нашому прикладі автомобіль 3 при цьому лишився `'в наявності'`.

## 9. Коли COMMIT у процедурі не потрібен

Головна причина існування процедур у PostgreSQL полягає в можливості виконувати `COMMIT` усередині, але вона потрібна не завжди. Процедура без `COMMIT` теж виконується як одна транзакція: якщо на якомусь кроці виникла помилка, скасовується **весь** виклик, включно з уже виконаними кроками.

```sql
CREATE PROCEDURE two_steps()
LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE cars SET status = 'тест' WHERE id = 3;
    RAISE EXCEPTION 'збій на другому кроці';
END;
$$;

CALL two_steps();
SELECT status FROM cars WHERE id = 3;
```

```text
ERROR:  збій на другому кроці
   status
-------------
 в наявності
```

Зміна статусу з першого кроку не збереглась. Це зручна поведінка за замовчуванням: «все або нічого» без жодного `BEGIN`/`COMMIT` у коді. Явний `COMMIT` додають лише тоді, коли потрібно навмисно зафіксувати частину роботи, наприклад під час обробки великого обсягу даних порціями (розділ 3). Процедура `sell_car` із розділу 7 нічого не фіксує частинами, тож `COMMIT` у ній, власне, не потрібен: без нього вона так само атомарна і, на відміну від версії з `COMMIT`, працює й усередині `BEGIN ... COMMIT`. Його залишено, щоб показати синтаксис.

## 10. Параметри за умовчанням і видалення процедури

Параметру процедури можна задати значення за умовчанням, і тоді при виклику його можна опустити:

```sql
CREATE PROCEDURE set_status(p_id INTEGER, p_status TEXT DEFAULT 'в наявності')
LANGUAGE plpgsql
AS $$
BEGIN
    UPDATE cars SET status = p_status WHERE id = p_id;
END;
$$;

CALL set_status(3);                 -- статус стане 'в наявності'
CALL set_status(3, 'в дорозі');     -- статус стане 'в дорозі'
```

Видаляють процедуру командою `DROP PROCEDURE`, і, як із функціями (Лекція 19), потрібно вказувати типи параметрів, бо процедури теж можуть бути перевантаженими: `DROP PROCEDURE set_status(INTEGER, TEXT);`. У виведенні `\df` процедури відрізняються від функцій значенням `proc` у колонці `Type`, а в колонці `Result data type` у них порожньо.

## 11. Запитання для самоперевірки

**Чи гарантує процедура `sell_car` із розділу 5, що один автомобіль не можна продати двічі?**

Ні. Процедура забезпечує атомарність пари `INSERT` і `UPDATE`, але не перевіряє статус автомобіля. Перевірку потрібно додати явно (розділ 7).

**Чому процедуру з `COMMIT` не можна викликати між `BEGIN` і `COMMIT` у клієнтському коді?**

Усередині явної транзакції процедура не має права її завершувати. PostgreSQL відповідає помилкою `invalid transaction termination`.

**Що станеться зі змінами, виконаними процедурою без `COMMIT`, якщо в ній виникне помилка?**

Скасується весь виклик цілком, зокрема й кроки, які встигли виконатися до помилки.

**У якому порядку розміщують перевірки й зміни даних у процедурі і чому?**

Спершу перевірки, потім зміни. Так некоректний запит відхиляється ще до того, як щось змінилося.

**Як відрізнити процедуру від функції в переліку `\df`?**

У колонці `Type` у процедури стоїть `proc`, а в функції `func`. Процедура не має типу результату.

## Підсумок

- `CREATE PROCEDURE ім'я(параметри) LANGUAGE plpgsql AS $$ ... $$;` —
  без `RETURNS`; викликається через `CALL`, а не `SELECT`.
- Спроба викликати процедуру через `SELECT` завершується чіткою
  помилкою з підказкою використати `CALL`.
- На відміну від функції, процедура МОЖЕ містити `COMMIT`/`ROLLBACK`
  усередині свого тіла — це і є головна причина, чому процедури
  існують окремо від функцій.
- Атомарну пару пов'язаних змін (Лекція 13) зручно оформити як
  процедуру — повторно використовуваний виклик замість ручного
  `BEGIN`/`COMMIT` щоразу.
- Бізнес-правила процедура перевіряє сама (`IF` і `RAISE EXCEPTION`) до внесення змін; сама атомарність не захищає від логічних помилок.
- Процедуру з `COMMIT` викликають поза явною транзакцією; без `COMMIT` помилка скасовує весь виклик.
