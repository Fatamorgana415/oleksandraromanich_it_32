# Лекція 14. Згенеровані стовпці: VIRTUAL і STORED

*Ціна з ПДВ, прапорець "чи продано", кількість днів до закінчення
терміну. Усе це похідні значення, які можна обчислити з уже наявних
колонок. Їх можна рахувати в кожному запиті окремо (`price * 1.2`), а
можна один раз оголосити прямо в структурі таблиці: тоді SQLite сам
рахує значення і сам гарантує, що воно завжди узгоджене з базовими
колонками.*

## 1. Проблема: похідне значення "вручну"

```sql
SELECT brand, price, price * 1.2 AS price_with_vat FROM cars;
```

Це працює, але формулу `price * 1.2` доведеться повторювати в КОЖНОМУ
запиті, де вона потрібна. Якщо ж хтось випадково збереже це значення
в окрему звичайну колонку через `UPDATE`, воно почне "розходитись" із
реальною ціною щоразу, коли `price` зміниться, а про синхронне
оновлення похідної колонки забудуть.

## 2. Згенерований стовпець (VIRTUAL) як рішення

```sql
ALTER TABLE cars ADD COLUMN price_with_vat REAL
    GENERATED ALWAYS AS (price * 1.2) VIRTUAL;

SELECT brand, price, price_with_vat FROM cars;
```

`GENERATED ALWAYS AS (вираз) VIRTUAL` оголошує колонку, значення якої
SQLite обчислює сам за формулою щоразу, коли до неї звертаються
(`SELECT`, `WHERE`), а не зберігає постійно на диску. Запит
`SELECT *` теж включає таку колонку з уже обчисленим значенням, як і
звичайну.

## 3. Згенеровану колонку неможливо змінити напряму

```sql
UPDATE cars SET price_with_vat = 1 WHERE id = 1;
```

```text
Parse error: cannot UPDATE generated column "price_with_vat"
```

Це і є гарантія узгодженості: ані `INSERT`, ані `UPDATE` не можуть
записати в згенеровану колонку довільне значення (обидві команди
завершуються помилкою). Єдиний спосіб змінити її значення
полягає у зміні колонки(ок), від яких вона обчислюється:

```sql
UPDATE cars SET price = 800000 WHERE id = 1;
SELECT price, price_with_vat FROM cars WHERE id = 1;
-- price_with_vat перерахувалось АВТОМАТИЧНО, без жодної додаткової команди
```

## 4. VIRTUAL проти STORED: важлива пастка

`VIRTUAL` (за умовчанням, якщо слово не вказано) обчислює значення
"на льоту" щоразу при зверненні, не займає місця на диску, але для
складної формули й частих запитів означає повторне обчислення щоразу.
`STORED` натомість фізично зберігає обчислене значення на диску (як
звичайну колонку) і перераховує його лише коли змінюються базові
колонки: швидший доступ при читанні, ціною місця на диску.

**Пастка:** `STORED` можна оголосити лише в
самому `CREATE TABLE`; додати `STORED`-колонку до вже існуючої
таблиці через `ALTER TABLE ADD COLUMN` **неможливо**:

```sql
ALTER TABLE cars ADD COLUMN is_sold INTEGER
    GENERATED ALWAYS AS (status = 'продано') STORED;
```

```text
Runtime error: cannot add a STORED column
```

Оскільки таблиці цього курсу вже існують (створені в Практиці 1/4), на
практиці для вже наявних таблиць доступний лише `VIRTUAL` варіант через
`ALTER TABLE`; `STORED` можливий лише якби таблиця створювалась
заново з цією колонкою від початку.

## 5. WHERE за згенерованою колонкою: як за звичайною

```sql
SELECT brand FROM cars WHERE price_with_vat > 900000;
```

Згенеровану колонку можна використовувати в `WHERE` (і в `ORDER BY`,
`GROUP BY`) так само, як і будь-яку звичайну. SQLite підставляє
формулу автоматично.

## 6. Згенеровані стовпці прямо в CREATE TABLE

У розділах 2 і 4 колонку додавали до вже наявної таблиці. Коли таблицю створюють заново, згенеровані стовпці оголошують разом з усіма іншими, і тут доступні обидва варіанти. Розглянемо таблицю товарів, де сума по позиції та підпис похідні від решти колонок:

```sql
CREATE TABLE products (
    id    INTEGER PRIMARY KEY,
    name  TEXT NOT NULL,
    price REAL NOT NULL,
    qty   INTEGER NOT NULL,
    total REAL GENERATED ALWAYS AS (price * qty) STORED,
    label TEXT GENERATED ALWAYS AS (name || ' (' || qty || ' шт.)') VIRTUAL
);

INSERT INTO products (name, price, qty) VALUES ('Зошит', 25.5, 10), ('Ручка', 12, 30);

SELECT * FROM products;
```

```text
id  name   price  qty  total  label
1   Зошит  25.5   10   255.0  Зошит (10 шт.)
2   Ручка  12.0   30   360.0  Ручка (30 шт.)
```

Колонку `total` оголошено як `STORED`: її значення обчислюється під час запису рядка й лежить на диску. Колонку `label` оголошено як `VIRTUAL`: вона обчислюється щоразу, коли до неї звертаються. Для користувача різниці немає, обидві виглядають як звичайні колонки. Змінимо кількість зошитів:

```sql
UPDATE products SET qty = 20 WHERE name = 'Зошит';

SELECT name, total, label FROM products;
```

```text
name   total  label
Зошит  510.0  Зошит (20 шт.)
Ручка  360.0  Ручка (30 шт.)
```

Після зміни `qty` обидві згенеровані колонки перерахувались самі, без жодної додаткової команди.

Слова `GENERATED ALWAYS` можна не писати: коротка форма `total REAL AS (price * qty) STORED` означає те саме.

У `INSERT` без переліку колонок згенеровані стовпці не враховуються. Для таблиці `products` потрібно вказати чотири значення (`id`, `name`, `price`, `qty`), а не шість; спроба передати шість завершиться помилкою `table products has 4 columns but 6 values were supplied`. Прямий запис у згенеровану колонку, як і в розділі 3, теж відхиляється: `cannot INSERT into generated column "total"`. Тому надійніше завжди перелічувати колонки явно.

## 7. Що можна писати у формулі

Формула згенерованої колонки підпорядкована трьом обмеженням.

Вона може використовувати **лише значення того самого рядка**: інші колонки цієї таблиці, константи, вбудовані функції. Звернутись до іншої таблиці не можна.

Вона має бути **детермінованою**, тобто для одних і тих самих вхідних значень завжди давати один результат. Функції `random()` чи `CURRENT_TIMESTAMP` недопустимі, бо їхній результат щоразу інший:

```sql
CREATE TABLE t (a INTEGER, b TEXT GENERATED ALWAYS AS (CURRENT_TIMESTAMP) VIRTUAL);
```

```text
Parse error: non-deterministic functions prohibited in generated columns
```

Підзапити у формулі також заборонені (`subqueries prohibited in generated columns`). Причина спільна: SQLite має гарантувати, що значення залежить тільки від рядка, і його можна обчислити в будь-який момент з однаковим результатом.

Зате формула може посилатись на **іншу згенеровану колонку**:

```sql
CREATE TABLE chain (a INTEGER, b INTEGER AS (a * 2), c INTEGER AS (b + 1));
INSERT INTO chain (a) VALUES (5);
SELECT * FROM chain;
```

```text
a  b   c
5  10  11
```

## 8. Індекс на згенерованій колонці

Згенерованій колонці можна дати індекс так само, як звичайній. Він корисний для обох видів колонок: значення в ньому вже впорядковані, тож SQLite не перебирає всі рядки.

```sql
CREATE INDEX idx_products_total ON products(total);

EXPLAIN QUERY PLAN SELECT * FROM products WHERE total > 100;
```

```text
SEARCH products USING INDEX idx_products_total (total>?)
```

Це ще один інструмент оптимізації з Лекції 13: коли в `WHERE` часто стоїть обчислений вираз, його зручно винести в згенеровану колонку й проіндексувати.

## 9. Як побачити згенеровані колонки в структурі таблиці

Команда `PRAGMA table_info(products)` показує лише звичайні колонки, згенеровані вона пропускає. Щоб побачити всі, використовують розширений варіант:

```sql
PRAGMA table_xinfo(products);
```

У результаті з'явиться додаткове поле `hidden`: значення 2 позначає `VIRTUAL`-колонку, а 3 позначає `STORED`. Повну формулу видно у виведенні `.schema products`.

## 10. Згенерована колонка чи подання

У Лекції 16 буде розглянуто подання (`VIEW`), яке теж дозволяє зберегти обчислення під іменем. Різниця в тому, **де** живе формула. Згенерована колонка належить таблиці й доступна в кожному запиті до неї, а подання створює окремий об'єкт, у якому можна поєднати кілька таблиць. Для похідного значення, що залежить лише від одного рядка, достатньо згенерованої колонки. Для складніших вибірок із `JOIN` потрібне подання.

Вибір між `VIRTUAL` і `STORED` залежить від співвідношення читання й запису. Якщо формула проста, а таблиця змінюється часто, обирайте `VIRTUAL`: дані не дублюються, запис не сповільнюється. Якщо формула дорога й значення читають значно частіше, ніж змінюють, обирайте `STORED`, але пам'ятайте, що це можливо лише під час створення таблиці.

## 11. Запитання для самоперевірки

**Чому не можна створити згенеровану колонку з формулою `CURRENT_TIMESTAMP`?**

Формула має бути детермінованою: значення залежить лише від даних рядка. `CURRENT_TIMESTAMP` щоразу дає новий час, тож результат не можна було б відтворити.

**У таблиці `products` змінили `price`. Чи потрібно вручну оновлювати колонку `total`?**

Ні, SQLite перераховує згенеровані колонки автоматично при зміні колонок, від яких вони залежать.

**Чим `STORED` відрізняється від `VIRTUAL` з погляду місця на диску й швидкості читання?**

`STORED` займає місце на диску й читається швидше, бо значення вже обчислено. `VIRTUAL` місця не займає, але обчислюється під час кожного звернення.

**Чому `INSERT INTO products VALUES (9, 'Y', 1, 1, 1, 'z')` завершується помилкою?**

Згенеровані колонки в такому `INSERT` не враховуються, тож таблиця очікує лише чотири значення, а передано шість. Крім того, записати значення в згенеровану колонку неможливо в принципі.

**Чи можна додати `STORED`-колонку до наявної таблиці командою `ALTER TABLE`?**

Ні, SQLite відповідає помилкою `cannot add a STORED column`. Для наявних таблиць доступний лише `VIRTUAL`.

## Підсумок

- `ALTER TABLE ... ADD COLUMN ім'я GENERATED ALWAYS AS (вираз) VIRTUAL`
  додає похідну колонку, яку SQLite рахує сам за формулою, без
  ризику розбіжності з базовими колонками.
- `INSERT`/`UPDATE` не можуть записати значення в згенеровану колонку
  напряму; єдиний спосіб її змінити полягає у зміні колонок, від яких вона
  залежить.
- `VIRTUAL` рахує "на льоту" (без місця на диску), `STORED` зберігає
  обчислене значення фізично, але `STORED` можна оголосити лише в
  `CREATE TABLE`, не через `ALTER TABLE` до вже наявної таблиці.
- Згенеровану колонку можна вільно використовувати в `WHERE`,
  `ORDER BY`, `GROUP BY`, так само, як і звичайну.
- Формула згенерованого стовпця має бути детермінованою й використовувати лише значення того самого рядка (без `random()`, `CURRENT_TIMESTAMP`, підзапитів).
- На згенерованому стовпці можна створити індекс, а `PRAGMA table_xinfo` показує такі стовпці серед інших.
