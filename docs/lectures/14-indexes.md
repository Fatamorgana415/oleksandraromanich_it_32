# Лекція 14. Індекси в SQLite. Оптимізація запитів, EXPLAIN

*Досі всі запити (`WHERE`, `JOIN`, `GROUP BY`) працювали правильно,
але СКІЛЬКИ рядків SQLite фактично переглядає, щоб знайти відповідь?
За умовчанням переглядає всі рядки таблиці підряд, навіть якщо в результаті один
рядок. Індекс дозволяє SQLite знайти потрібні рядки напряму, без
повного перегляду таблиці, а `EXPLAIN QUERY PLAN` показує, який саме
план SQLite обрав для конкретного запиту.*

## 1. Проблема: повний перегляд таблиці (SCAN)

```sql
EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE customer_id = 3;
```

```text
SCAN orders
```

`EXPLAIN QUERY PLAN` перед будь-яким запитом (замість виконання
запиту) показує ПЛАН, за яким SQLite буде його виконувати, а не
результат самого запиту. `SCAN orders` означає: SQLite переглядає
**рядок за рядком усю таблицю** `orders`, перевіряючи умову
`customer_id = 3` у кожному, навіть якщо таблиця має мільйон рядків
і відповідних лише 5.

## 2. CREATE INDEX: прямий шлях до потрібних рядків

```sql
CREATE INDEX idx_orders_customer ON orders(customer_id);
```

```sql
EXPLAIN QUERY PLAN
SELECT * FROM orders WHERE customer_id = 3;
```

```text
SEARCH orders USING INDEX idx_orders_customer (customer_id=?)
```

`CREATE INDEX ім'я ON таблиця(колонка)` будує окрему допоміжну
структуру (по суті впорядкований "покажчик"), що дозволяє SQLite
відразу знайти рядки з потрібним значенням колонки, а не перевіряти
кожен рядок таблиці по черзі. Після створення індексу той самий запит
показує в плані `SEARCH ... USING INDEX` замість `SCAN`.

## 3. Композитний індекс на кілька колонок одразу

```sql
-- умова відразу на ДВОХ колонках
SELECT * FROM orders WHERE customer_id = 3 AND status = 'a';
-- з лише idx_orders_customer(customer_id) — індекс частково допомагає,
-- SQLite звужує пошук за customer_id, а status все ще перевіряє рядок за рядком

CREATE INDEX idx_orders_customer_status ON orders(customer_id, status);
```

```text
SEARCH orders USING INDEX idx_orders_customer_status (customer_id=? AND status=?)
```

Індекс можна будувати одразу на кількох колонках через кому: тоді
план запиту показує, що ОБИДВІ умови (`customer_id=?` і `status=?`)
використали індекс напряму, без додаткової рядок-за-рядком перевірки
другої умови.

## 4. Індекс і сортування без окремого кроку

```sql
CREATE INDEX idx_orders_date ON orders(order_date);

EXPLAIN QUERY PLAN
SELECT * FROM orders ORDER BY order_date;
```

```text
SCAN orders USING INDEX idx_orders_date
```

Індекс корисний не лише для `WHERE`: оскільки дані в індексі вже
впорядковані за значенням колонки, `ORDER BY` за проіндексованою
колонкою може скористатись цим готовим порядком, замість того, щоб
спершу зібрати всі рядки, а потім сортувати їх окремим кроком.

## 5. DROP INDEX і перегляд наявних індексів

```sql
DROP INDEX idx_orders_customer;

SELECT name, tbl_name FROM sqlite_master WHERE type = 'index';
```

`DROP INDEX ім'я` видаляє індекс (сама таблиця й дані не змінюються,
лише зникає прискорювальна структура). Список усіх наявних у базі
індексів можна отримати із системної таблиці `sqlite_master`
(`type = 'index'`).

## 6. Індекс не завжди безкоштовний

Індекс прискорює `SELECT`, але має свою ціну: він займає додаткове
місце на диску і сповільнює кожен `INSERT`/`UPDATE`/`DELETE` у
проіндексовану колонку (базі потрібно оновити не лише саму таблицю,
а й структуру індексу). Тому індекси варто створювати цілеспрямовано:
на колонках, за якими справді часто фільтрують чи сортують (типово це
зовнішні ключі факт-таблиці, як у прикладах вище), а не "на всяк
випадок" на кожній колонці.

## 7. Як працює індекс

Найближча аналогія: предметний покажчик у кінці підручника. Щоб знайти, де згадується певний термін, не потрібно гортати всю книгу сторінка за сторінкою: у покажчику терміни стоять за алфавітом, поруч із кожним записано номери сторінок. Індекс бази даних влаштований так само: це окрема впорядкована структура, у якій кожному значенню колонки відповідає посилання на рядок таблиці.

Усередині SQLite індекс зберігається як **B-дерево**: структура, у якій значення розкладено по рівнях, як у картотеці (шафа, шухляда, картка), і на кожному рівні відкидається більшість варіантів. Схоже на гру «вгадай число від 1 до мільйона» з підказками «більше» чи «менше»: вистачить близько 20 спроб, а не мільйона. Тому з ростом таблиці кількість кроків пошуку зростає дуже повільно.

Деякі індекси SQLite створює без вашої участі. Первинний ключ `INTEGER PRIMARY KEY` уже є найшвидшим способом знайти рядок, а для кожного обмеження `UNIQUE` (Лекція 6) автоматично створюється службовий індекс:

```sql
CREATE TABLE users (id INTEGER PRIMARY KEY, email TEXT UNIQUE, name TEXT);

EXPLAIN QUERY PLAN SELECT * FROM users WHERE email = 'a@b.c';
```

```text
SEARCH users USING INDEX sqlite_autoindex_users_1 (email=?)
```

## 8. Наскільки індекс прискорює пошук

Для оцінки створимо таблицю `orders` з мільйоном рядків, де `customer_id` набуває 50 000 різних значень, і виконаємо запит на підрахунок замовлень одного клієнта:

```sql
SELECT COUNT(*) FROM orders WHERE customer_id = 777;
```

Без індексу SQLite переглядає всю таблицю, і на тестовому комп'ютері це зайняло близько 0,03 секунди. Після `CREATE INDEX idx_c ON orders(customer_id)` той самий запит виконується менш ніж за мілісекунду. Створення самого індексу коштувало близько 0,26 секунди: це одноразова плата, після якої кожен пошук стає швидшим. Точні цифри залежать від комп'ютера, а різниця на порядки зберігається.

На маленькій навчальній таблиці з десятком рядків різниці ви не помітите, і саме тому `EXPLAIN QUERY PLAN` корисніший за вимірювання часу: він показує **спосіб** виконання запиту, який на великих даних і визначає швидкість.

## 9. Коли індекс не допомагає

Створити індекс замало: SQLite скористається ним лише тоді, коли умова запиту має відповідний вигляд. Нижче типові випадки на прикладі таблиці `orders` з попередніх розділів.

**Композитний (складений) індекс працює зліва направо.** Нехай є індекс `idx_orders_customer_status ON orders(customer_id, status)`. Він корисний, коли в умові задано `customer_id`, окремо або разом зі `status`. Але запит лише за другою колонкою індекс не використовує:

```sql
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE status = 'a';
```

```text
SCAN orders
```

Аналогія з телефонним довідником: його впорядковано спершу за прізвищем, потім за іменем. За прізвищем знайти людину легко, а за одним лише іменем довелося б переглядати всю книгу. Тому в складеному індексі першою ставлять колонку, за якою фільтрують найчастіше.

**Вираз над колонкою вимикає індекс.** Навіть якщо індекс на `customer_id` існує, запит із арифметикою над колонкою його ігнорує:

```sql
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE customer_id + 1 = 4;
```

```text
SCAN orders
```

SQLite не вміє «розгорнути» вираз і дізнатись, який `customer_id` дасть 4. Вихід простий: перенести арифметику на інший бік рівності, тобто `WHERE customer_id = 3`. Те саме стосується функцій: умова `strftime('%Y', order_date) = '2025'` теж призводить до `SCAN`, хоча на `order_date` є індекс. Є два виходи: переписати умову як діапазон, `order_date >= '2025-01-01' AND order_date < '2026-01-01'`, після чого план зміниться на `SEARCH ... USING INDEX idx_orders_date`, або створити індекс саме на виразі:

```sql
CREATE INDEX idx_orders_year ON orders(strftime('%Y', order_date));
```

**Пошук за шаблоном `LIKE`.** Умова `note LIKE '%99'` не може скористатись індексом, бо початок значення невідомий, і впорядкованість індексу нічого не дає. Індекс упорядковано з урахуванням регістру («Київ» і «київ» стоять у різних місцях), а `LIKE` у SQLite за умовчанням регістр ігнорує, тому скористатися порядком індексу він не може: навіть умова `note LIKE 'note99%'` із відомим початком дає `SCAN`. Для точного збігу пишіть `note = 'note99'`.

**Мало різних значень.** Індекс на колонці, де лише кілька значень (скажімо, три статуси замовлення), майже не допомагає: кожне значення збігається з третиною таблиці, а читати третину рядків через індекс не швидше, ніж переглянути всю таблицю, і навіть повільніше: для кожного рядка доводиться стрибати між індексом і таблицею.

## 10. Покривальний індекс

Іноді запиту взагалі не потрібно звертатись до таблиці: усі потрібні колонки вже є в індексі. Тоді в плані з'являється слово `COVERING`:

```sql
EXPLAIN QUERY PLAN
SELECT customer_id, status FROM orders WHERE customer_id = 3;
```

```text
SEARCH orders USING COVERING INDEX idx_orders_customer_status (customer_id=?)
```

Це найшвидший варіант: SQLite читає лише індекс, а рядки таблиці не чіпає. Запит `SELECT *` покривальним бути не може, бо в індексі немає решти колонок. Ще одна причина вибирати у `SELECT` лише потрібні колонки, а не `*`.

Якщо з кількох індексів підходить будь-який, вибір робить сам SQLite. Нехай знову існує й `idx_orders_customer`: для запиту `SELECT * ... WHERE customer_id = 3` SQLite обере саме його, а для запиту вище, що читає лише `customer_id` і `status`, покривальний `idx_orders_customer_status`. Тому, подивившись план, завжди перевіряйте, **який саме** індекс обрано.

## 11. Запитання для самоперевірки

**У плані запиту стоїть `SCAN orders`. Що це означає і чи завжди це погано?**

SQLite переглядає всі рядки таблиці. Для маленької таблиці це нормально й навіть швидко, для великої таблиці й частого запиту це сигнал подумати про індекс.

**На таблиці є індекс `(customer_id, status)`. Чи прискорить він запит `WHERE status = 'a'`?**

Ні. Складений індекс використовується лише тоді, коли в умові є його перша колонка. Для запиту за `status` потрібен окремий індекс, або інший порядок колонок, якщо за `status` фільтрують частіше.

**Чому `WHERE customer_id + 1 = 4` ігнорує індекс на `customer_id`, а `WHERE customer_id = 3` використовує?**

Індекс упорядковано за значеннями самої колонки, а не за результатом виразу. Щоб скористатись індексом, умову потрібно записати безпосередньо для колонки.

**Скільки індексів варто створити на таблиці, що часто змінюється?**

Якомога менше, лише для тих колонок, за якими справді шукають. Кожен індекс сповільнює `INSERT`, `UPDATE` і `DELETE` та займає місце на диску (розділ 6).

**Що означає `COVERING INDEX` у плані запиту?**

Усі колонки, потрібні запиту, є в самому індексі, тож SQLite не звертається до таблиці. Це найшвидший спосіб читання.

## Підсумок

- `EXPLAIN QUERY PLAN` показує ПЛАН виконання запиту, а не його
  результат. `SCAN таблиця` означає повний перегляд рядок за рядком,
  `SEARCH ... USING INDEX` означає прямий пошук через індекс.
- `CREATE INDEX ім'я ON таблиця(колонка)` будує допоміжну структуру для
  швидкого пошуку за значенням колонки; можна вказати кілька колонок
  одразу для композитного індексу.
- Індекс за проіндексованою колонкою прискорює й `ORDER BY`, уникаючи
  окремого кроку сортування.
- `DROP INDEX` видаляє індекс без втрати даних; `sqlite_master` (тип
  `'index'`) показує всі наявні індекси бази.
- Індекс має свою ціну (місце на диску, повільніші зміни даних); його
  варто створювати цілеспрямовано, а не на кожній колонці підряд.
- SQLite використовує індекс не завжди: композитний індекс працює зліва направо, а вираз над колонкою чи `LIKE '%...'` призводять до `SCAN`.
- `COVERING INDEX` у плані означає, що всі потрібні колонки є в самому індексі й до таблиці звертатись не довелось.
