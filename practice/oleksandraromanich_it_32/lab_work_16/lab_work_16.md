## Завдання 3. Перенесення в реальну таблицю

**Перенесення (з фільтрацією рядка заголовків):**

```sql
INSERT INTO books (title, author, publication_year, genre, copies_count)
SELECT field1, field2, field3, field4, field5
FROM books_staging
WHERE field1 != 'title';
```

**Результат:**

```
Execution finished without errors.
Result: query executed successfully. Took 0ms, 8 рядків постражджало
```

**Видалення проміжної таблиці:**

```sql
DROP TABLE books_staging;
```

**Перевірка кількості після імпорту:**

```sql
SELECT COUNT(*) AS books_after FROM books;
```

**Результат:**

```
books_after
-----------
32
```

**Перевірка приросту:** було **24**, стало **32**. Різниця: **32 − 24 = 8**. Це точно дорівнює кількості рядків у CSV-файлі (8 нових книг). **Імпорт пройшов успішно.**

## Завдання 5. Свідома помилка прямого імпорту

**Підготовка:** щоб не зіпсувати робочу базу, було створено копію `lab_work3.db` → `lab_work_16_test.db`. Спроба виконана в **копії**.

**Спроба прямого імпорту в цільову таблицю `books`:**

```sql
.mode csv
.import --skip 1 new_rows.csv books
```

**Що сталося — точний текст повідомлення:**

```
v1_new_rows.csv:2: expected 6 columns but found 5 - filling the rest with NULL
v1_new_rows.csv:2: INSERT failed: datatype mismatch
v1_new_rows.csv:3: expected 6 columns but found 5 - filling the rest with NULL
v1_new_rows.csv:3: INSERT failed: datatype mismatch
v1_new_rows.csv:4: expected 6 columns but found 5 - filling the rest with NULL
v1_new_rows.csv:4: INSERT failed: datatype mismatch
... (і так для кожного з 8 рядків)
```

**Пояснення:**
- **CSV-файл має 5 колонок:** `title`, `author`, `publication_year`, `genre`, `copies_count`.
- **Таблиця `books` має 6 колонок:** `id`, `title`, `author`, `publication_year`, `genre`, `copies_count`.
- `.import` розкладає значення **за порядком**, а не за назвою: перше значення файлу йде в **першу** колонку таблиці (у `id`).
- Назва книги `'Тіні забутих предків і сьогодення'` намагається потрапити в `id` (тип `INTEGER PRIMARY KEY`). SQLite намагається привести рядок до числа — не вдається → **помилка `datatype mismatch`**.

**Перевірка, що рядки не додалися:**

```sql
SELECT COUNT(*) FROM books;
```

Результат: **24** — те саме число, що й до спроби. **Жоден рядок не імпортувався.**

**Чому це не працює безпосередньо:**
- **Різна кількість колонок** — CSV без `id`, таблиця з `id`. `.import` розкладає значення **за позицією**, а не за назвою.
- **Зсув на одну колонку** — усі значення зсуваються ліворуч на 1 позицію. Назва книги → `id`, автор → `title`, рік → `author` тощо. Типи не збігаються — помилка.
- **`id` не можна довільно вказувати** — номери з файлу можуть збігтися з уже зайнятими (конфлікт `UNIQUE`).

**Висновок:** прямий імпорт у цільову таблицю **неможливий** без проміжної таблиці. Правильний підхід — `books_staging` (без `id`), потім `INSERT ... SELECT` — саме те, що ми зробили в Завданнях 2–3.

## Контрольні питання

### 1. Чому CSV-файл цієї практики навмисно не містить колонку id: що б сталося, якби спробувати додати її туди самостійно з довільними значеннями?

**Колонка `id` — це сурогатний первинний ключ, який SQLite генерує автоматично.** Його значення має бути **унікальним** і **не залежати від зовнішніх даних**.

**Що сталося б, якби додати `id` у CSV довільно:**
- Якщо вказати `id = 1, 2, 3...`, а в таблиці вже є такі `id` — виникне конфлікт `UNIQUE constraint failed`. Рядки не додадуться.
- Якщо вказати «великі» `id` (наприклад, 1000, 1001...) — вони «перестрибнуть» через наявні й залишать «дірки» в нумерації.
- Якщо вказати **однакові** `id` для різних рядків — конфлікт `UNIQUE`.
- Якщо вказати `id`, який **менший** за наявні — може порушити логіку автоінкременту.

**Головна проблема:** CSV — це **зовнішні дані**, і ми **не знаємо**, які `id` уже зайняті в таблиці. Покладатися на «довільні» значення — ризиковано: конфлікт унікальності, пропуски в нумерації, порушення порядку.

**Правильний підхід:** **не вказувати `id` у CSV**. Нехай SQLite сам призначить наступні номери після найбільшого наявного. Це гарантує унікальність, безперервність нумерації, відсутність конфліктів.

### 2. Яка роль DROP TABLE проміжної таблиці в кінці процесу: чи можна просто залишити її в базі «про всяк випадок»?

**`DROP TABLE books_staging` — це обов'язковий крок очищення**, а не «опціональний».

**Причини, чому не можна залишати:**

1. **Дублювання при повторному імпорті.** Якщо залишити `books_staging` і наступного разу виконати `.import` у неї — нові рядки додадуться до старих. Після цього `INSERT INTO books SELECT * FROM books_staging` перенесе **всі** рядки — і старі, і нові — **удруге** в `books`. Виникнуть дублікати.

2. **Зайве місце на диску.** Проміжна таблиця з тисячами рядків займає місце. Після перенесення вона не потрібна.

3. **Плутанина в схемі.** `books_staging` — це технічний артефакт, а не частина бізнес-моделі. Інші розробники будуть плутатися, що це за таблиця.

4. **Порушення принципу атомарності.** Процес імпорту має бути завершеним: створити staging → імпортувати → перенести → **видалити staging**. Якщо staging залишається — процес «незавершений».

**Висновок:** `DROP TABLE books_staging` — **обов'язковий** крок. Він робить процес імпорту **атомарним і чистим**.

### 3. Чим підрахунок COUNT(*) до й після імпорту (Завдання 1 і 3) кращий за враження «здається, що імпорт спрацював»?

**`COUNT(*)` — це об'єктивна перевірка, а «здається» — це ілюзія.**

**Що дає `COUNT(*)` до й після:**
1. **Точне число** — не «десь 30», а конкретно `24 → 32`.
2. **Очікуваний приріст** — ми знаємо, що в CSV 8 рядків. Різниця має бути **рівно 8**. Якщо не 8 — щось пішло не так.
3. **Автоматичність** — `COUNT(*)` виконується SQLite, а не людиною.

**Чому «здається, що імпорт спрацював» — ненадійно:**
- **`SELECT` може показати неповний результат** — ви побачили 3 нові рядки, але не помітили, що 5 інших не додалися.
- **`.import` не завжди повідомляє про помилки** — якщо частина рядків впала, `.import` може «пройти» без явних помилок.
- **Візуальна перевірка обмежена** — ви бачите 10 рядків, але не знаєте, чи правильно розподілені колонки.
- **Людська помилка** — «здається, що все добре» — суб'єктивне відчуття.

**`COUNT(*)` — це «істина в останній інстанції»:**
- Якщо до = 24, після = 32, різниця = 8 → **імпорт успішний**.
- Якщо різниця = 5 → **3 рядки не додалися** → треба перевіряти.
- Якщо різниця = 16 → **імпорт виконався двічі** → треба виправляти.

**Висновок:** `COUNT(*)` до й після — це **об'єктивна, автоматична, точна** перевірка. Вона краща за «здається», бо не залежить від людського ока, дає конкретне число для порівняння й одразу показує, чи є проблема.
