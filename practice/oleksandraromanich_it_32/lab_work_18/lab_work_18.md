# Практика 18. Згенеровані стовпці у SQLite

**Варіант № 1 — Бібліотека**

**Файл бази:** `lab_work_18.db`

## Завдання 1. Похідне числове значення

**Команда:**

```sql
ALTER TABLE books ADD COLUMN total_value INTEGER
    GENERATED ALWAYS AS (copies_count * 100) VIRTUAL;
```

**Пояснення формули:** У бібліотеці один примірник книги умовно оцінюється у 100 гривень (наприклад, для внутрішнього обліку вартості фонду). Згенерований стовпець `total_value` обчислює **загальну вартість усіх примірників цієї книги** в каталозі: `copies_count * 100`.

**Перевірка:**

```sql
SELECT id, title, copies_count, total_value FROM books LIMIT 5;
```

**Результат:**

```
id | title                                   | copies_count | total_value
---+-----------------------------------------+--------------+------------
1  | Кобзар                                  | 11           | 1100
2  | Місто                                   | 7            | 700
3  | Тіні забутих предків                    | 5            | 500
4  | 1984                                    | 15           | 1500
5  | Гаррі Поттер і філософський камінь      | 20           | 2000
```

Значення `total_value` автоматично обчислюється на основі `copies_count` кожного рядка — жодних ручних вставок чи оновлень не потрібно.

## Завдання 2. Похідний логічний прапорець

**Команда:**

```sql
ALTER TABLE readers ADD COLUMN is_active INTEGER
    GENERATED ALWAYS AS (CASE WHEN registration_date >= '2025-01-01' THEN 1 ELSE 0 END) VIRTUAL;
```

**Пояснення:** У таблиці `readers` є колонка `registration_date` (дата реєстрації). Логічний прапорець `is_active` показує, чи читач є «новим» (зареєстрований у 2025 році або пізніше) — `1` для нових, `0` для тих, хто зареєструвався раніше.

**Перевірка:**

```sql
SELECT id, last_name, registration_date, is_active FROM readers LIMIT 5;
```

**Результат:**

```
id | last_name  | registration_date | is_active
---+------------+-------------------+----------
1  | Шевченко   | 2024-09-01        | 0
2  | Коваленко  | 2024-09-15        | 0
3  | Бондаренко | 2024-10-03        | 0
4  | Ткаченко   | 2024-11-12        | 0
5  | Мельник    | 2025-01-08        | 1
```

Значення `is_active` відповідає реальному стану рядка: для читачів із 2024 року — `0`, для 2025 — `1`.

> **Примітка щодо NULL:** Якби `registration_date` було `NULL`, то `NULL >= '2025-01-01'` дало б `NULL`, і `CASE WHEN NULL THEN 1 ELSE 0 END` повернуло б `0` (бо `CASE` вважає `NULL` хибністю). Але якби формула була просто `registration_date >= '2025-01-01'` без `CASE`, то для `NULL` результат був би `NULL`. У нашій таблиці `registration_date` має `NOT NULL`, тому цей випадок не виникає.

## Завдання 3. Свідома помилка прямого запису

**Спроба:**

```sql
UPDATE books SET total_value = 500 WHERE id = 1;
```

**Точний текст помилки (скопійовано з DB Browser):**

```
Execution finished with errors.
Result: cannot UPDATE generated column: total_value
At line 1:
UPDATE books SET total_value = 500 WHERE id = 1;
```

SQLite не дозволяє напряму змінювати згенерований стовпець — він обчислюється автоматично, і його значення не можна перезаписати.

---

## Завдання 4. Автоматичний перерахунок

**До UPDATE:**

```sql
SELECT id, title, copies_count, total_value FROM books WHERE id = 1;
```

```
id | title   | copies_count | total_value
---+---------+--------------+------------
1  | Кобзар  | 11           | 1100
```

**UPDATE базової колонки:**

```sql
UPDATE books SET copies_count = 10 WHERE id = 1;
```

**Після UPDATE:**

```sql
SELECT id, title, copies_count, total_value FROM books WHERE id = 1;
```

```
id | title   | copies_count | total_value
---+---------+--------------+------------
1  | Кобзар  | 10           | 1000
```

**Висновок:** значення `total_value` **змінилося автоматично** — з `1100` на `1000`, синхронно зі зміною `copies_count` з 11 на 10. Жодної додаткової команди для оновлення згенерованого стовпця не знадобилося — SQLite перерахував його сам.

## Завдання 5. WHERE за згенерованим стовпцем

**Запит:**

```sql
SELECT id, title, copies_count, total_value
FROM books
WHERE total_value > 1500;
```

**Результат:**

```
id | title                                   | copies_count | total_value
---+-----------------------------------------+--------------+------------
4  | 1984                                    | 15           | 1500
5  | Гаррі Поттер і філософський камінь      | 20           | 2000
```

**Обґрунтування:** запит `WHERE total_value > 1500` **простіший і зрозуміліший**, ніж повторення формули: `WHERE copies_count * 100 > 1500`. По-перше, формула може бути складною (множення, ділення, кілька колонок) — і повторювати її в кожному запиті втомливо й ризиковано (легко зробити помилку). По-друге, зміна формули (наприклад, вартість примірника змінилася зі 100 на 120) вимагала б редагування **кожного запиту**, де використовується ця формула. Зі згенерованим стовпцем формула зберігається **в одному місці** — в означенні колонки, і всі запити автоматично використовують актуальне значення.

## Контрольні питання

### 1. Чому в цій практиці можна створити лише VIRTUAL, а не STORED згенеровану колонку і що саме в наявній таблиці цьому заважає?

**`ALTER TABLE ADD COLUMN` у SQLite підтримує лише `VIRTUAL` згенеровані колонки, а не `STORED`.** Це обмеження самої SQLite: при додаванні колонки до **вже існуючої** таблиці SQLite не може перерахувати значення для всіх наявних рядків і зберегти їх на диску — це вимагало б перезапису всієї таблиці, що суперечить принципу «легких» міграцій у SQLite.

**Що заважає:** У нашій таблиці `books` уже є **22 рядки** (або 32 після Практики 16). Якби ми спробували додати `STORED` колонку, SQLite мав би для кожного з цих рядків **обчислити й зберегти** значення `total_value`. Але `ALTER TABLE` у SQLite не підтримує таку операцію — тому дозволено лише `VIRTUAL`, яка обчислюється «на льоту» при кожному запиті.

**`VIRTUAL` vs `STORED`:**
- `VIRTUAL` — значення обчислюється при кожному `SELECT` (не зберігається на диску). Менше місця, але повільніше при частих запитах.
- `STORED` — значення обчислюється при `INSERT`/`UPDATE` і зберігається на диску. Швидше при читанні, але займає місце й не підтримується в `ALTER TABLE ADD COLUMN`.

### 2. Що станеться, якщо спробувати видалити (DROP COLUMN) базову колонку, від якої залежить згенерований стовпець?

**SQLite видасть помилку й заблокує видалення.** Згенерований стовпець `total_value` залежить від `copies_count` — якщо видалити `copies_count`, формула `copies_count * 100` стане невалідною.

**Точний текст помилки (очікуваний):**
```
Execution finished with errors.
Result: error in generated column "total_value": no such column: copies_count
```

**Що це означає:** SQLite перевіряє залежності між згенерованими й базовими колонками. Ви не можете видалити колонку, від якої залежить інша — спочатку треба видалити згенеровану колонку, а потім базову.

**Правильний порядок:**
1. `ALTER TABLE books DROP COLUMN total_value;` — видалити згенеровану.
2. `ALTER TABLE books DROP COLUMN copies_count;` — видалити базову.

### 3. Чому неможливість прямого INSERT чи UPDATE у згенеровану колонку (Завдання 3) є перевагою, а не обмеженням?

**Це перевага, бо гарантує цілісність даних.** Згенерована колонка — це **похідне значення**, яке має бути **завжди** результатом формули. Якби можна було вручну записати туди довільне значення:
- **Порушувалася б логіка.** Наприклад, `total_value` мало б дорівнювати `copies_count * 100`. Якщо хтось запише `total_value = 500`, а `copies_count = 11`, то значення в колонці не відповідатиме формулі — і всі звіти, що базуються на цій колонці, стануть недостовірними.
- **Доводилося б синхронізувати вручну.** При кожній зміні `copies_count` треба було б окремо оновлювати `total_value`. Забув — і отримав розбіжність.
- **Збільшувалася б імовірність помилок.** Людський фактор: хтось випадково оновить `total_value` не тим значенням — і ніхто не помітить.

**Автоматичний перерахунок** (Завдання 4) гарантує, що `total_value` **завжди** відповідає `copies_count` — без жодного ручного втручання. Це і є перевага: **менше роботи, менше помилок, більше довіри до даних**.

**Аналогія:** згенерована колонка — як формула в Excel (`=A1*100`). Ви не можете ввести в клітинку `B1` довільне число, якщо там стоїть формула, — Excel перезапише його при зміні `A1`. Це не «обмеження», а **гарантія**, що `B1` завжди відповідає `A1`.
